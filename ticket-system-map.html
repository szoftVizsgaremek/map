Framework, library, build tool: what's the difference?

These words get mixed up all the time, even by professionals. The classic distinction is about who is in control:

  • Library: a collection of code that you call when you need it. You decide the structure of the app. Example: we call formatDate(), useQuery(), z.object().
  • Framework: a ready-made structure that calls your code. You fill in the gaps it leaves, following its rules. This is called inversion of control ("don't call us, we'll call you").
  • Meta-framework: a framework built around a UI library that also decides routing, data loading, server rendering and the build. Examples for React: Next.js, React Router in "framework mode".
  • Build tool: not part of the app at all. It prepares the code (Vite).

So is React a framework?

Officially, no. React calls itself "the library for web and native user interfaces". It only handles one job, which is turning data into UI. It doesn't decide how you do routing, data fetching, forms or styling. That's why our package.json has a separate library for each of those jobs.

In everyday speech, people still say "React framework", and job ads list React under "frameworks". You'll also hear React called "unopinionated", meaning it leaves those choices to you. A framework like Angular is "opinionated": it comes with its own router, forms and HTTP client already chosen. Our team made those choices itself, so in practice, React + Vite + our chosen libraries plays the role a framework would.

HTML and CSS

the page itself, and how it looks

In one sentence: HTML describes what is on a page (headings, buttons, boxes), and CSS describes how it looks (colours, sizes, spacing). Every web page uses both. In our app we write very little of either by hand: React builds the HTML from JSX, and Tailwind writes most of the CSS.

HTML is the furniture in a room, CSS is the paint and the arrangement. JSX is how we order the furniture; Tailwind is a catalogue of ready-made paint jobs.

Our only HTML file

  • (1) A small piece of plain JavaScript that runs before anything else and switches dark mode on if needed, so the page doesn't flash white. See Dark mode.
  • (2) The empty box React fills with the whole app. Every page you see lives inside this one <div>; that's what "single-page application" means.
  • (3) Loads our TypeScript entry file. The browser can't run .tsx, so Vite translates it on the way (see Vite). type="module" allows import/export.
  • The <head> holds information about the page (character set, tab icon, title, phone scaling); the <body> holds what you see.

Our CSS file → more in Tailwind CSS

  • Almost all our CSS comes in through these @import lines: Tailwind, the animation classes, shadcn's styles and the Geist font.
  • The rest of the file defines our colours as design tokens for light and dark mode. The Tailwind section explains it line by line.
  • There are no other .css files to look for: components get their look from the className lists in the JSX.

JavaScript

the language the browser actually runs

In one sentence: JavaScript is the programming language built into every web browser. Chrome, Firefox and Safari all understand it, and nothing else. Everything else on this page is either a layer on top of JavaScript or a tool that produces JavaScript.

Think of JavaScript as the base language everyone speaks. TypeScript and JSX are like a teacher's notes written in the margin: helpful while writing, but they get erased before the text is handed in.

Where you meet plain JavaScript in our project

  • eslint.config.js: the settings for the code-style checker (npm run lint). A real .js file, no types.
  • The small script inside index.html: it reads the saved theme ("vite-ui-theme") from localStorage and switches dark mode on before React starts, so the page doesn't flash white. It is plain JavaScript because it runs straight in the browser, with no Vite translation step.
  • All the code the browser receives. When you open DevTools → Sources while npm run dev runs, the files you see there are JavaScript that Vite translated from our .ts/.tsx files.
  • Node.js is JavaScript outside the browser. It runs npm, Vite, Vitest and the mariadb_backend.

JavaScript features used all over our code

Most of what you read in our .ts files is ordinary JavaScript. Here is src/lib/api-client.ts, trimmed. Only the parts with the TypeScript highlight (see the legend under the code) are TypeScript; everything else is plain JavaScript.

TypeScript only (deleted before the browser sees it)

  • package.json says "type": "module": our files use modern import/export instead of the older require() style you see in some backend code.

TypeScript

JavaScript + type labels, checked before the app runs

In one sentence: TypeScript is JavaScript where you may write down what kind of value something is (a number, one of seven role names, a Ticket object…), and a checker called tsc warns you when the code doesn't match.

Like labels on drawers in a workshop. The labels don't change what's inside, they just stop you putting a screwdriver in the drawer marked "fuses". Before the app ships, all labels are peeled off.

The most important fact about TypeScript

Types exist only while you write and build. The browser never sees them. So TypeScript catches mistakes in our code early, but it cannot check what the backend really sends at runtime. That's why the backend still validates everything itself.

Real example: role-routing.ts

Press the buttons to see what you write versus what the browser gets after Vite has removed the types.

  • role: Role | undefined means "role is one of the seven role names, or nothing at all (not signed in)". The | reads as "or".
  • : string after the brackets says the function always returns text.
  • import type imports only a label. The whole line disappears in the browser version, because there is nothing left to import.
  • If someone wrote homeRouteFor("admn") (typo), the editor underlines it in red: "admn" is not a Role. Without TypeScript, it would silently return "/profile".

JSX

HTML-looking tags written inside JavaScript

In one sentence: JSX lets you describe a piece of the screen with tags that look like HTML, right inside your code. It is not HTML and the browser can't read it: a tool translates every tag into a normal JavaScript function call.

JSX is shorthand. Writing <Badge>Critical</Badge> is like writing "ASAP" instead of "as soon as possible". It means the same thing, it's just quicker to read.

What a tag turns into

So a JSX tag is "call this component with these inputs". The attributes (variant=…) become the props object. What's between the opening and closing tag becomes children. The jsx() function comes from React, which is why JSX and React almost always appear together.

SQL

the language the database understands
MariaDB

MariaDB is an open-source relational database management system (RDBMS) and a community-developed fork of MySQL. It stores the project's data, such as tickets and users, in tables made of rows and columns, and runs as a separate server process next to the backend. The frontend never connects to it directly: only the backend does, by sending SQL queries, which the rest of this section explains.

In one sentence: SQL (Structured Query Language, said "S-Q-L" or "sequel") is how a program asks a database to find, add, change or delete rows in its tables. Our tickets and users live in a MariaDB database, and only the backend talks to it.

The database is a huge filing cabinet of tables. SQL is the request slip you hand to the archivist: "bring me the user card with this username".

A real query from the Node backend

  • (1) Read it as English: "select every column from the users table where the username equals …". SELECT reads; INSERT, UPDATE and DELETE add, change and remove rows.
  • (2) The ? is a placeholder. The database fills it in safely, so a username full of quotes can't change the query (this prevents SQL injection).
  • In the Node backend, SQL is written by hand inside JavaScript strings. In the Java backend you rarely see SQL: JPA writes it from Java classes (see A request's journey).
  • The two backends use separate databases, one for Node and one for Java, so test data in one doesn't show up in the other.

TanStack Query

server-state library: loading, caching and refreshing backend data

In one sentence: TanStack Query (formerly called React Query) fetches data from the backend, remembers it in a cache under a name (the query key), tells your component whether it's still loading or failed, and fetches it again when it might be out of date.

Like a good assistant with a notebook. You ask "what are the tickets?" The assistant writes the answer under the heading "tickets", and the next time anyone asks, it reads the notebook instantly while quietly phoning the backend to check for changes. When you say "I just created a ticket", it crosses out the "tickets" page so it gets re-checked.

Why not just use fetch + useState?

You could, and AuthProvider actually does that for the signed-in user. For everything else, you'd have to hand-write the loading flag, the error flag, the "don't update if the page was closed" check, retries, sharing data between pages, and refreshing after changes. TanStack Query gives you all of that, and it's the same on every page.

Reading data: useQuery

  • const { data: tickets, isLoading } = … is JavaScript destructuring with a rename: "take data and call it tickets".
  • While loading (or after an error) tickets is undefined. tickets ?? [] uses the nullish coalescing operator: "if it's undefined or null, use an empty list".
  • The type of tickets is inferred from fetchMyTickets's return type (Promise<Ticket[]>), so TypeScript knows it's Ticket[] | undefined without being told.

Changing data: useMutation + invalidation

  • queryFn: () => fetchTicket(ticketId) is wrapped in an arrow function because fetchTicket needs an argument. In MyTicketsPage, fetchMyTickets needs none, so it's passed directly.
  • enabled: Number.isFinite(ticketId): the id comes from the URL as text and is turned into a number. If the URL is /tickets/abc, the number is NaN, so the query doesn't run at all (a dependent query).
  • The status type is written out by hand ("open" | "in_progress" | "closed"). It means exactly the same as our TicketStatus type, so using TicketStatus here would be a small tidy-up.
  • disabled={statusMutation.isPending} stops double clicks while the request is on its way.

After the backend confirms the change, the ticket's cache entry is invalidated. The useQuery for that ticket notices, fetches again, and React re-renders with the new status. Nobody had to update the screen by hand.

Polling: the notification bell

refetchInterval: 30_000 asks the backend again every 30 seconds, so a new notification shows up without a page reload.

Emptying the cache on logout

Interesting detail: AuthProvider itself does not use useQuery for "who is signed in?". It uses plain useState + useEffect, which is a perfectly normal choice for one value that the whole app depends on.

React Hook Form

form library: values, validation, errors, submit

In one sentence: React Hook Form (often shortened to RHF) is a library, used through the useForm hook, that keeps track of what's typed into a form, checks it, shows error messages next to the right fields, and only calls your submit code when everything is valid.

A clerk at a counter who takes your paper form, checks every box against the rules sheet (that's Zod), hands it back with red marks if something's wrong, and only passes it to the back office (the backend) once it's complete.

Our project uses RHF in two different styles

Useful to know when reading the real files: the Login page and the Create Ticket page connect their inputs to RHF in two different ways. Both are correct.

Style A: register (LoginPage)

  • register("username") returns { name, onChange, onBlur, ref }, and {...register("username")} spreads them onto the input. RHF then reads the value straight from the browser's input: an uncontrolled input.
  • The error message is shown by hand: {errors.username && <p>…</p>} is conditional rendering of errors.username.message.
  • noValidate turns off the browser's own pop-up validation, so only our Zod messages appear.
  • aria-invalid={errors.username ? true : undefined} tells screen readers the field has an error. undefined means the attribute is left out.
  • LoginPage also keeps its own isSubmitting and submitError in useState, and its onSubmit is an async function with try / catch / finally around login(values).

Style B: FormField wrappers (CreateTicketPage)

  • FormField uses RHF's Controller inside, so here the value lives in React: a controlled field. {...field} passes value, onChange, onBlur, name and ref.
  • <FormMessage /> finds and shows this field's error by itself, through context. No hand-written error paragraph is needed.
  • render={({ field }) => …} is the render prop pattern: you hand over a function, and the library calls it with what you need.
  • The submit callback is written inline. It runs only after Zod is happy, then reshapes the values: an empty description becomes "", and the assignee text becomes a Number or null. ...values is spread: copy all fields, then override two.
  • name="name" is type-checked against CreateTicketFormValues, so a typo in a field name is a build error.

Reacting to a field: useWatch + setValue

useWatch re-renders when the chosen Type changes, so the Assignee list can be narrowed straight away. The useEffect is a side effect with a dependency array ([selectedAssigneeId, assignableUsers, form]): it runs again whenever one of those changes and clears an assignee who is no longer allowed.

Our wrapper: components/ui/form.tsx

shadcn/ui generated these thin wrappers so every form looks the same and is accessible. They all talk to RHF through context.

Zod

schema validation library: rules that still exist when the app runs

In one sentence: Zod lets you describe the shape and rules of data in a schema ("username: text, at least 3 characters"), then check real data against it while the app is running, and it can also produce the matching TypeScript type from that schema.

TypeScript is the building plan, checked before construction. Zod is the security guard at the door, checking every person who actually walks in. The plan can't stop a stranger; the guard can.

Why we need it if we already have TypeScript

Remember that TypeScript types are erased at build time. What a user types into a form only exists at runtime, so TypeScript can never check it. Zod is real JavaScript code that survives into the browser, so it fills exactly that gap. It's the only "type check" in our app that runs in the user's browser.

Our two real schemas

  • Each field has two .min() rules on purpose. An empty field fails both, and RHF shows the first message ("Username is required"). Typing one or two letters fails only the second ("…at least 3 characters"). Two rules give two different, clearer messages.
  • The last line is the clever part. z.infer creates a TypeScript type from the schema, so the rules and the type can never drift apart. That type is given to useForm<LoginFormValues>, which is how RHF knows the field names.
  • z.enum([...], { message: "Type is required" }) sets the error text for this whole rule. Zod 4 still accepts message, but its newer documentation writes it as error.

Setup: a plugin and one CSS file

Tailwind 4 needs no tailwind.config.js (that's why components.json has "config": ""). It's switched on in two places.

  • (1) brings in Tailwind's preflight (a CSS reset that removes browser default margins and styles) and all utility classes. Only the classes found in our files end up in the final CSS.
  • (2) adds classes like animate-in and fade-in that shadcn uses for menus and popups. The spinning animate-spin on Loader2 is plain Tailwind.
  • (4) is why font-sans means "Geist Variable" in our app (set in @theme inline below). The font file comes from our own server, not Google.
  • main.tsx imports ./index.css, so this one file is the whole stylesheet of the app.

@apply uses Tailwind classes inside a CSS file. These three rules set the default border colour, page background, text colour and font for everything, so components only need classes where they differ. @layer base puts them at the lowest priority, so any class in a component wins over them.

Design tokens: why our classes say "primary" and not "blue-600"

Plain Tailwind has colour classes like bg-blue-600. Our code almost never uses them. It uses semantic colour names (named by role, not by look): background, foreground, primary, muted, destructive… These are design tokens, defined in three steps in index.css.

  • The chain: bg-primary → --color-primary → var(--primary) → the value in :root or .dark. Change one line in :root and every primary button in the app changes colour.
  • That's why the "Sign in" button is steel-indigo in light mode and rose-pink in dark mode with the same bg-primary class.
  • oklch(L C H) is a CSS colour format: lightness (0 to 1), chroma (how colourful), hue (an angle, 0 to 360). Hue 262 is blue-indigo, 340 to 355 is pink. Lightness is predictable to the eye, so light/dark pairs are easy to tune.
  • Each colour comes in a pair: primary for the background, primary-foreground for text on top of it. Using the pair keeps the text readable in both themes.
  • The chart-1 to chart-5 and sidebar-… tokens are shadcn defaults. We don't use charts or a sidebar yet.

Dark mode: from the toggle button to the colours

  1. You click the Sun/Moon button in the navbar. It calls toggleTheme from useTheme().
  2. ThemeProvider (src/components/theme-provider.tsx) changes its state theme to "light" or "dark". It can also be "system", which follows the operating system; that's the default.
  3. Its useEffect calls applyTheme(theme) and saves the choice in localStorage under the key vite-ui-theme.
  4. applyTheme (src/lib/theme.ts) does one thing (see the code below): it adds or removes the class dark on <html>.
  5. CSS takes over. .dark { … } in index.css swaps every token value, and @custom-variant dark (&:is(.dark *)) makes every dark: class active for elements inside .dark.
  6. hidden dark:block on the Sun and dark:hidden on the Moon: React never decides which icon to show. CSS does.

Try it: open DevTools → Elements, click the theme button, and watch class="dark" appear and disappear on the <html> line. In DevTools → Application → Local Storage you'll see vite-ui-theme change too. The small theme script in index.html reads the same key before React starts, so the page doesn't flash white on reload.

shadcn/ui: Tailwind components that live in our own folder

shadcn/ui is not a normal library you import from node_modules. Its command-line tool (shadcn in devDependencies) copies the source code of a component into src/components/ui/, and from then on it's our code. components.json tells the tool where to put things ("ui": "@/components/ui"), that we write .tsx, and that icons come from lucide. Our style is "base-nova", which builds on Base UI (@base-ui/react): unstyled components that handle behaviour and accessibility, with Tailwind adding the looks.

  • cva (class-variance-authority) turns variant="ghost" size="icon" into the right class string. The navbar's theme and logout buttons use exactly that: <Button variant="ghost" size="icon">.
  • VariantProps<typeof buttonVariants> makes TypeScript know the allowed values. variant="blue" would fail the build.
  • cn() joins class strings and settles conflicts: if the base says px-2.5 and you pass className="px-6", the result keeps only px-6. We get it from the npm package cn (^0.2.5), made by the shadcn author as a faster drop-in for the usual clsx + tailwind-merge pair. src/lib/utils.ts is one line, export { cn } from "cn"; the navbar imports it from @/lib/utils, while button.tsx and badge.tsx import "cn" directly. Same function either way.
  • The ticket-status badges work the same way, with badge-variants.ts and <Badge variant=…>.

React Router's NavLink passes isActive. The link of the page you're on gets a grey background; the others are grey text that darkens on hover.

Vite

the dev server and the builder

In one sentence: Vite (French for "quick", said "veet") is the tool that takes our .ts/.tsx files and serves them to the browser as JavaScript while you develop, and packs them into a few small files when you build for production.

Vite is the kitchen. TypeScript and JSX are the raw ingredients, React is the recipe, and the browser is the customer who only eats finished plates (JavaScript). Vite cooks to order while you develop, and prepares the whole menu in advance when you build.

Vite's two jobs

npm run devStarts a server on http://localhost:5173. When the browser asks for /src/main.tsx, Vite translates just that file to JavaScript on the spot. Save a file and the page updates in about a second, without a full reload (called hot module replacement).
npm run buildRuns tsc -b first (type check only), then vite build, which translates every file, joins them, shrinks them, and writes them into the dist/ folder. npm run preview lets you try that result.

Is Vite only the tool that started the project?

No. Two different things carry the name "Vite", and it's easy to mix them up. One is used once, to create a new project. The other is the real Vite, which stays in the project and works every day.

CommandWhenWhat it really isStill in the project afterwards?
npm create vite@latestonce, at the very starta project template copier (scaffolding): it copies a ready-made starter project into a new folder, then exitsno, only the files it copied stay, including vite.config.ts and "vite" in devDependencies

So the starter command is gone after day one, but Vite itself is the engine that turns our TypeScript and JSX into runnable JavaScript, every time the app runs, gets built or gets tested. In the kitchen picture above: the starter command only built the kitchen on day one; Vite is the kitchen you cook in every day, for the app and for the tests alike.

Our vite.config.ts, line by line

  1. Plugins. react() teaches Vite to translate JSX and to keep component state during hot updates. tailwindcss() turns the className="…" style names into real CSS.
  2. The @ shortcut. import … from "@/features/auth/permissions" means src/features/auth/permissions.ts. This line is for Vite (to find the file). The matching paths line in tsconfig.app.json is for TypeScript (to check it). Both must agree.
  3. The proxy. The browser only talks to :5173. Any request starting with /api or /uploads is quietly forwarded by Vite to the backend on :8080 (Node today, Java later). That's why the frontend code can just call fetch("/api/tickets"), and why there are no CORS errors in development.

Vitest: Vite's test runner

Our tests (npm test → vitest run) use Vitest, made by the Vite team. Test files are .ts and .tsx too, and Node can't run those directly, so they must be translated first. Vitest doesn't bring its own translator: it uses Vite's, and reads vite.config.ts too, so tests get the same @/ shortcut and the same JSX translation for free, exactly as the real app gets them. Things that trip people up

  • "Vite" is not just the starter. npm create vite runs once and is gone; Vite itself runs on every npm run dev, npm run build and (through Vitest) npm test.

  • Port 5173 is the frontend, 8080 is the backend. Open 5173 in the browser. If the backend isn't running, the login page loads but signing in fails.

Build time vs run time

This is the single most useful distinction for understanding the tools on this map. Some things happen once, on a developer's machine. Others happen every time a user opens the page.

Build time / compile time

On your computer, in Node.js, before anyone uses the app.

  • TypeScript checks types (tsc)
  • ESLint checks code style
  • Vite transpiles TS/TSX and transforms JSX
  • Vite bundles, minifies and tree-shakes
  • Tailwind generates the CSS
  • Vitest runs the tests

Mistakes found here cost nothing: the user never sees them.

Run time

In the user's browser, every time the page is opened.

  • The JavaScript engine runs the bundle
  • React renders components and updates the DOM
  • React Router picks the page for the URL
  • fetch talks to the backend
  • TanStack Query caches the answers
  • Zod validates form input

No types exist here any more. Zod is the only "type check" that survives into the browser, because it's real JavaScript code.

A request's full journey

from a click to MariaDB and back: the Node backend today, the Java backend later

Everything so far happens in the browser. But the tickets themselves live in a MariaDB database, and only the backend may talk to it. The frontend and the backend talk over HTTP: the frontend sends a request (method + path + maybe a JSON body), the backend sends back a response (a status code + usually a JSON body). The backend that runs today is written in Node.js; the plan is to switch to the Java one, which answers on the same address.

Ordering in a restaurant. You (the browser) never walk into the kitchen. You give your order to the waiter (the Vite proxy), the cook (the backend) checks your table number (the session cookie), takes things from the pantry (MariaDB), and the plate comes back the same way.

Step by step: signing in, then loading the ticket list

  1. LoginPage → login(values) in AuthProvider → login() in auth.api.ts → apiFetch("/api/auth/login", { method: "POST", body: JSON.stringify(credentials) }).
  2. apiFetch calls the browser's fetch with credentials: "include" (send and accept cookies) and the header Content-Type: application/json.
  3. The request goes to localhost:5173/api/auth/login. The Vite proxy forwards it to localhost:8080. To the browser, everything comes from one address, so there's no cross-origin problem.
  4. The backend looks up the username in MariaDB and compares the password with the stored bcrypt hash. Wrong: 401 with {"message": "Invalid username or password"}.
  5. Right: it makes a random session token, remembers "token → user id" in memory, and answers 200 with the user as JSON plus a Set-Cookie: session=…; HttpOnly; SameSite=Lax header.
  6. The browser stores the cookie. Because it's HttpOnly, our JavaScript can't read it, which protects it from scripts injected by an attacker.
  7. Next, the Dashboard's useQuery calls apiFetch("/api/tickets"). The browser attaches the cookie automatically.
  8. The backend reads the cookie, finds the user for that token (no token or unknown token: 401), checks the role (admin: 403), runs a SQL query, and returns the tickets as JSON.
  9. apiFetch turns the JSON into objects, TanStack Query caches them under ["tickets"], and React draws the list.

Things that trip people up

  • Port 8080 is taken: only one backend can run at a time. Stop Node before starting Java, or the second one fails to start.
  • Signed out for no reason? Either the session cookie expired or the backend was restarted (sessions are in memory).
  • A page works with Node and not with Java: check the endpoint table above first. A 404 in DevTools → Network on an /api/… path usually means "this backend doesn't have it".
  • The frontend hides a button, but the API still allows it (or the other way round): the backend's answer is the one that counts. API tests with curl check it directly.
